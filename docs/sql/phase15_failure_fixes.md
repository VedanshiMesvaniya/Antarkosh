# Query-failure fixes (from the qts_ais diagnostic): why answers came back empty or wrong, and what changed

Each item is a universal fix (no database, table or question is named in the code) and is safe to leave on for every database.

| # | Symptom in the logs | Root cause | Fix | Where |
|---|---|---|---|---|
| 1 | `sqlglot could not parse DDL ... Falling back to raw DDL` (16+ per question) | Two chunk shapes never parsed: a `-- Table:` header in front of `TABLE x (...)` hid the `TABLE` keyword, and the `FOREIGN KEY` lines appended after the closing `)` are not valid SQL. Raw DDL cost tokens, and `extract_join_hints` failed silently on the same chunks. | One shared pre-parse step: drop whole-line comments, `TABLE` to `CREATE TABLE`, fold trailing foreign-key lines inside the table. Compaction and join hints both use it. | `src/sql/schema_compactor.py` |
| 2 | `Tables without valid join path` then a hallucinated join (`qn_number = prinbr`) returning 0 rows | The real link was inferred from names only (score ~0.55-0.60, below the 0.70 publish threshold) so it never reached `relationships.json`, and no prompt reads `inferred_relationships.json`. The published graph is deliberately NOT loosened. | When a query that joined disconnected tables comes back empty, the repair prompt now also receives the medium-confidence inferred links that would connect them (direct first, else through one bridge table), labelled unverified. A query that returns rows is never touched. | `src/sql/repair/advisory_links.py`, `src/sql/generation.py` |
| 3 | Empty result classed `valid_empty` and never repaired | Any query with a `WHERE` counted as legitimate emptiness, even when the validator had flagged disconnected tables. | `classify_empty_result(..., disconnected_tables=...)`: a join over tables with no defined relationship is `suspicious_empty` (default behaviour unchanged). | `src/sql/safety/empty_result_classifier.py` |
| 4 | "SQL result cache hit" returned the same empty answer instantly | Empty results were cached (SQL result cache and semantic cache) for the whole TTL, so asking again could not recover. | Empty answers are no longer cached in either cache; real answers still are. | `src/sql/pipeline.py`, `src/pipeline/query.py` |
| 5 | `last 90 days` returns nothing; the table's newest row is months or years old | Correct SQL against data that ends earlier. "No data found" said nothing about why. | For an already-empty result that compares a column with the current date, one cheap `SELECT MAX(col)` (5 s timeout, at most 2 columns) appends "the newest `col` value in `table` is DATE (N days before today)". Nothing is retried or rewritten. | `src/sql/safety/data_recency.py` |
| 6 | "QN history" retrieved `qc_main` | "QN" appears only as the start of key columns (`qn_number`), so nothing routed it. | The sync generates a whole-word anchor rule for a short abbreviation that starts the single-column key of exactly one table and is carried by other tables. The router gets an opt-in `"whole_word": true`; plain rules match as before. | `src/sql/semantics/routing.py`, `src/sql/table_router.py` |
| 7 | OpenRouter 404 on every call; `gpt-oss-20b` empty with `max_tokens=120` | Dead free models (and the default pin `openrouter_text_model`); a reasoning model spends its token budget thinking. | New verified free models in `config/providers.yaml`; a reasoning model asked for fewer than 1024 tokens gets 1024 (others unchanged). | `config/providers.yaml`, `src/core/config.py`, `src/core/provider_client.py` |

## Deliberately not done

* `result_validator` still returns WARNING (not CRITICAL) for tables with no valid path. Making it fatal would block valid joins in every database whose relationships are incomplete (most MSSQL databases have no foreign keys). The empty-result path above uses the same signal safely instead.
* The 0.70 publish threshold and `relationships.json` are untouched.
* Rewriting `GETDATE()` to the data's own latest date is not done: it silently changes what the user asked. The note tells the user instead.
