# Query-failure fixes (from the qts_ais diagnostic): why answers came back empty or wrong, and what changed

Each item is a universal fix (no database, table or question is named in the code) and is safe to leave on for every database.

| # | Symptom in the logs | Root cause | Fix | Where |
|---|---|---|---|---|
| 1 | `sqlglot could not parse DDL ... Falling back to raw DDL` (16+ per question) | Two chunk shapes never parsed: a `-- Table:` header in front of `TABLE x (...)` hid the `TABLE` keyword, and the `FOREIGN KEY` lines appended after the closing `)` are not valid SQL. Raw DDL cost tokens, and `extract_join_hints` failed silently on the same chunks. | One shared pre-parse step: drop whole-line comments, `TABLE` to `CREATE TABLE`, fold trailing foreign-key lines inside the table. Compaction and join hints both use it. | `src/sql/schema_compactor.py` |
| 2 | `Tables without valid join path` then a hallucinated join (`qn_number = prinbr`) returning 0 rows | The real link was inferred from names only (score ~0.55-0.60, below the 0.70 publish threshold) so it never reached `relationships.json`, and no prompt reads `inferred_relationships.json`. The published graph is deliberately NOT loosened. | When a query that joined disconnected tables comes back empty, the repair prompt now also receives the medium-confidence inferred links that would connect them (direct first, else through one bridge table), labelled unverified. A query that returns rows is never touched. | `src/sql/repair/advisory_links.py`, `src/sql/generation.py` |
| 3 | Empty result classed `valid_empty` and never repaired | Any query with a `WHERE` counted as legitimate emptiness, even when the validator had flagged disconnected tables. | `classify_empty_result(..., disconnected_tables=...)`: a join over tables with no defined relationship is `suspicious_empty` (default behaviour unchanged). | `src/sql/safety/empty_result_classifier.py` |
| 4 | "SQL result cache hit" returned the same empty answer instantly | Empty results were cached (SQL result cache and semantic cache) for the whole TTL, so asking again could not recover. | Empty answers are no longer cached in either cache; real answers still are. | `src/sql/pipeline.py`, `src/pipeline/query.py` |
| 5 | `last 90 days` returns nothing; the table's newest row is months or years old | Correct SQL against data that ends earlier. "No data found" said nothing about why. | For an already-empty result that compares a column with the current date, one cheap `SELECT MAX(col)` (5 s timeout, at most 2 columns) appends "the newest `col` value in `table` is DATE (N days before today)". Nothing is retried or rewritten. | `src/sql/safety/data_recency.py` |
| 6 | "QN history" retrieved `qc_main` | "QN" appears only as the start of key columns (`qn_number`), so nothing routed it. | The sync generates a whole-word anchor rule for a short abbreviation that starts the single-column key of exactly one table and is carried by other tables. The router gets an opt-in `"whole_word": true`; plain rules match as before. | `src/sql/semantics/routing.py`, `src/sql/table_router.py` |
| 7 | OpenRouter 404 on every call; `gpt-oss-20b` empty with `max_tokens=120` | Dead free models (and the default pin `openrouter_text_model`); a reasoning model spends its token budget thinking. | New verified free models in `config/providers.yaml`; a reasoning model asked for fewer than 1024 tokens gets 1024 (others unchanged). | `config/providers.yaml`, `src/core/config.py`, `src/core/provider_client.py` |

## Deliberately not done

* `result_validator` still returns WARNING (not CRITICAL) for tables with no valid path. Making it fatal would block valid joins in every database whose relationships are incomplete (most MSSQL databases have no foreign keys). The empty-result path above uses the same signal safely instead.
* The 0.70 publish threshold and `relationships.json` are untouched.
* Rewriting `GETDATE()` to the data's own latest date is not done: it silently changes what the user asked. The note tells the user instead.

## Round 2 (live telemetry of 2026-11-16)

| # | Symptom | Root cause | Fix | Where |
|---|---|---|---|---|
| 8 | `400 Bad Request` on `gemini-3.5-flash-lite` | The model exists (GA), but Google changed its API from 3.5 Flash-Lite / 3.6 on (`thinking_level` replaces `thinkingBudget`); this client always sends `thinkingBudget: 0`. My earlier addition of that model was wrong for this client. | Removed from every chain. A test now fails if a Gemini model newer than 3.1 is configured while the client keeps this request format. | `config/providers.yaml`, `tests/core/test_provider_free_models.py` |
| 9 | Provider order | Gemini first everywhere burned its 15 requests/min; OpenRouter was pinned first by `DEFAULT_PROVIDER` to the front of every task, even large thinking. | Everyday tasks: openrouter (Gemma 4, Google's open model; OpenRouter has no free Gemini) -> groq -> nvidia -> gemini last. Large thinking (reasoning, repair, synthesis): gemini first, backups are other providers' reasoning models (Nemotron 3 Ultra on NVIDIA then OpenRouter, gpt-oss-120b on Groq). `DEFAULT_PROVIDER` default and `render.yaml` are now `auto`; set the same in your `.env`. | `config/providers.yaml`, `src/core/config.py`, `render.yaml` |
| 10 | `active = '1'` where the column holds `'Y'`/`'N'` returned 0 rows and was accepted | Nothing tells the model how a flag is stored; the empty answer passed as valid. | For an already-empty result, one `SELECT DISTINCT` (max 11 rows, 5 s) per column compared with a literal. If the column has at most 10 values and the literal is not one, the note "`t.active` only holds 'N', 'Y'; the query filtered it with '1'" goes to the repair prompt and the answer. A repair is forced only when the literal is a flag/number guess ('1', true, 'Y'); a named value like "Boston" is just explained. | `src/sql/safety/value_check.py`, `src/sql/generation.py` |
| 11 | Sync keeps files built by older code | `RULESET_VERSION` numbers are bumped by hand; a forgotten bump keeps stale generated files until the database itself changes. | A fingerprint of the phase sources (line endings ignored) is recorded with the phase versions; any code change reruns the skippable phases once. Unchanged code still skips. | `src/sql/sync/drift.py` |
| 12 | Sync batches drain the free quota | Column meaning shares the `extraction` task with interactive questions, so with OpenRouter first its few free requests a day would go to the sync. | Own task `schema_sync`: NVIDIA, Groq, OpenRouter, Gemini last. | `src/sql/sa/meaning_phase.py`, `config/providers.yaml` |

Restart the server after applying: a running process keeps the old code and the old `providers.yaml`, which is why the earlier telemetry still showed dead OpenRouter slugs and the compactor warnings.

## Round 3 (Terra's plan checked against the code)

Terra's plan was verified claim by claim. Confirmed and fixed (smallest change each); a new `SQLRequestContext` object, a full type validator, SQLGlot pre-normalization and failure-type repair routing were NOT built: the bugs below are scoping slips, not a missing object, and the executor already normalizes.

| # | Confirmed problem | Fix | Where |
|---|---|---|---|
| 13 | The result validator was built without the database's relationships and fell back to the DEFAULT (ERP) database's: every join of another database looked "disconnected" (this also fed the empty-result classifier of round 1). | `ResultValidator(..., relationships=)`; the pipeline passes `get_raw_relationships(self.db_id)`. Callers that pass nothing keep the old fallback. | `src/sql/safety/result_validator.py`, `src/sql/pipeline.py` |
| 14 | `record_deleted CHAR(1)` was never detected as a soft-delete marker. | `<noun>_deleted` / `<noun>_removed` count as a flag when the TYPE is char(1), boolean or bit (not counts, not `undeleted`). | `src/sql/soft_delete_spec.py` |
| 15 | The enforcement treated ANY predicate on the marker as "already written", so `record_deleted IS NULL`, `= 0`, `= '0'` on a 'Y'/'N' column passed through and returned nothing. | Typed check: a form the column's type cannot hold is replaced by the real condition (`IN ('N','n') OR IS NULL`); right forms are left byte-identical. | `src/sql/soft_delete_spec.py` |
| 16 | The generic prompt told every database to use `alias.deleted_at`. | For a non-ERP database in apply mode the soft-delete lines point to the typed per-table condition instead. `erp_main` and non-apply modes are unchanged. | `src/sql/prompt_builder.py` |
| 17 | The repair prompt carried no dialect. | One line: target database and how it writes a row limit (derived with sqlglot, about 25 tokens). Not added for `erp_main`. | `src/sql/generation.py` |
| 18 | After generation plus three repairs every call was used, so the answer-writing call was refused. | The synthesis call is not held back by the call count (the token ceiling still applies). | `src/utils/query_budget.py`, `src/core/provider_client.py` |

Immediate workaround without a resync (curated file, supported today): `databases/qts_ais/semantics/soft_delete.json` listing `sqts_main_lear` with `record_deleted`.

## Round 4 (the three items skipped in round 3, now built)

All of it is active only in **strict mode**: a database other than `erp_main` that runs the Phase 12 prompt flags in apply mode (`auto_prompt_inject`). `erp_main` and every database outside apply mode behave exactly as before (only the new `sql_request_context` telemetry event is added).

| # | What | How | Where |
|---|---|---|---|
| 19 | **`SQLRequestContext`**: one immutable object per request with the dialect profile, this database's relationships, soft-delete specs, column types and enum values, and `strict`. | Built in `SQLRetriever._retrieve_with_delta_repair` and passed to `execute_with_delta_repair`. Consumers read from it: the repair dialect line, soft-delete enforcement (`enforce_soft_delete_filter(..., specs=)`), the type validator. Every loader is best effort (a missing file is an empty value), so building it cannot fail a query. | `src/sql/request_context.py`, `src/sql/pipeline.py`, `src/sql/generation.py`, `src/sql/soft_delete.py` |
| 20 | **SQL normalisation**: the statement written the way the target dialect spells it (`LIMIT n` to `TOP n`, `::` casts, `FETCH FIRST` on Oracle). | `normalize_sql` after every generation and repair. The executor still parses and serialises (defence in depth), so executed SQL is the same. | `src/sql/safety/sql_normalize.py` |
| 21 | **Type validator**: reports comparisons the database rejects or can never match: number column vs text, date column vs text with no date, text column vs number, bit/enum column vs a value outside its set, joins between columns of different families. | A certain error (number or date column vs text on SQL Server, PostgreSQL, Oracle) is CRITICAL and stops the query before the database; everything else is a warning that makes an EMPTY answer suspicious and puts the problem into the repair prompt. It never rewrites a query. | `src/sql/safety/type_check.py` |
| 22 | **Failure-type repair routing**: a syntax error that re-spelling cures needs no model call. | Borrowed syntax the target parser rejects (TOP on MySQL, backticks on SQL Server) used to be DROPPED by the early syntax check; it is now re-spelled first. A syntax error raised by the database is re-spelled before the model is asked. Everything else (missing column, bad join, semantics) still goes to the model. | `src/sql/safety/sql_normalize.py`, `src/sql/generation.py` |
| 23 | **Sync warning for a soft-delete setting that names a column the catalog does not have.** | In sync validation, as a WARNING (never an error, never a rollback): `db.yaml soft_delete.column` that is in no table, and curated `semantics/soft_delete.json` entries whose table or column is missing. It also lists the markers the catalog does contain. The template's own default `deleted_at` is reported only when the catalog has other markers, so a database with no soft delete does not warn on every sync. | `src/sql/sync/validate.py` |

Why the warning matters: a curated or atlas soft-delete entry is applied without checking the column exists. If it names a missing column the enforcement adds it to every query on that table and the database answers "Invalid column name": the table cannot be queried at all. A `db.yaml` declaration that is a typo silently filters nothing, so deleted rows come back in answers. Neither is visible anywhere today.
